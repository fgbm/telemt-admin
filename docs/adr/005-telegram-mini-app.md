# ADR 005: Telegram Mini App как второй интерфейс бота

## Статус

Принято (2026-09-28).

## Контекст

Бот управляется через чат: slash-команды, inline-экраны, wizard. Для пользователя это неудобно при работе со ссылками (копирование, QR, инструкция по WEB-прокси), для администратора — при работе со списками заявок, пользователей и токенов. Telegram Mini App даёт полноценный интерфейс внутри клиента Telegram с авторизацией пользователя без паролей.

## Решение

- Встроенный HTTP-сервер (`axum`) в том же процессе `telemt-admin`, модуль `src/webapp/`: общий `BotState` (SQLite, backend `telemt`, конфиг), без второго сервиса и второй БД.
- Сервер слушает `webapp.listen` (по умолчанию `127.0.0.1:8090`) и публикуется только через HTTPS reverse proxy (Caddy/NGINX). TLS внутри процесса не терминируется.
- Авторизация каждого запроса `/api/*`: заголовок `Authorization: tma <initData>`, проверка подписи Telegram (`HMAC-SHA256`, ключ `HMAC("WebAppData", bot_token)`), сравнение за постоянное время, `auth_date` не старше `webapp.init_data_max_age_secs` (по умолчанию 1 ч, допустимо 60 с…24 ч) и не из будущего (допуск 60 с). Сессий, cookie и собственных токенов нет.
- Права администратора — те же `admin_ids`, что у бота; проверяются на каждом админском запросе.
- Доменные операции (одобрение, отклонение, удаление, токены, выдача ссылок) переиспользуются из `bot::handlers` через узкие `pub(crate)` re-export, чтобы бот и приложение вели себя одинаково и писали одинаковые уведомления.
- Ввод invite-токена в приложении не дублирует flow бота: приложение открывает deep link `t.me/<bot>?start=<token>`, токен обрабатывает бот.
- Фронтенд — статические HTML/CSS/JS без сборщика, вшитые в бинарник (`include_str!`); DOM строится через `textContent`. Заголовки: CSP (`script-src 'self' https://telegram.org`, `frame-ancestors` Telegram Web), `nosniff`, `no-referrer`, `Cache-Control: no-store` для API.
- Кнопка меню бота (`setChatMenuButton`, WebApp) ставится при старте, если задан HTTPS `webapp.public_url`.

## Отвергнутые альтернативы

- Отдельный сервис с собственной БД/API — дублирование доменной логики и синхронизации с `telemt`.
- SPA-фреймворк со сборкой — лишняя цепочка поставки и зависимостей для нескольких экранов.
- Сессионные cookie/JWT — `initData` уже подписан Telegram и короткоживущий; собственные токены добавили бы хранилище секретов.

- Все ответы — с `Cache-Control: no-store`, `nosniff`, `no-referrer` (слой на весь роутер); тело запроса ограничено 8 КБ; авторизация выполняется до разбора тела.
- Одобрения из бота и приложения сериализуются одной блокировкой в процессе (иначе двойной provision в `telemt` с разными секретами).
- Кнопка меню ведёт в приложение, только если HTTP-сервер реально открыл порт; иначе ставится стандартная кнопка.

## Инварианты

- Без `webapp.enabled = true` HTTP-сервер не запускается, поведение бота не меняется.
- `/api/*` без валидного `initData` возвращает 401, админские эндпоинты для не-админа — 403.
- `initData`, ссылки и секреты пользователей не пишутся в логи.
- HTTP-сервер не слушает публичный интерфейс без TLS-терминатора перед ним.

## Последствия

- Новая публичная поверхность (через reverse proxy): её нужно мониторить и держать за файрволом.
- Утечка `bot_token` позволяет подделать `initData` — токен бота становится ключом и для приложения.
- `admin_ids` управляют и ботом, и приложением.
