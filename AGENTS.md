# AGENTS.md

Persistent rules for AI agents working on `telemt-admin` — a Telegram bot (plus Telegram Mini App) that manages access to the `telemt` MTProto proxy.

Read as needed: `docs/overview.md` (invariants), `docs/architecture.md` (module map), `docs/development.md` (CI, conventions, which docs to update), `docs/adr/` (decisions), `docs/runbook.md` (operations).

## Working rules

- Reply to the user in Russian. User-facing bot/Mini App texts are Russian; `tracing` logs are English with structured context.
- Keep changes minimal; no new dependencies or unrelated refactoring without a clear need.
- No `unwrap()` on errors that can be expected or external.
- Commits: Conventional Commits. Changelog is generated by `git-cliff`.
- When a change touches architecture, `telemt` integration, security, config, notifications or operational behavior, update the docs listed under «Конвенции» in `docs/development.md` in the same series of changes.

Before finishing notable changes (CI runs the same plus `cargo audit`):

```bash
cargo fmt
cargo test --locked
cargo check --locked
cargo clippy --all-targets -- -D warnings
```

## Architecture boundaries

- `src/telemt_backend/` is the only entry point for talking to `telemt`. It is API-first (control API) with a legacy fallback (`telemt.toml` + runtime reload, ADR 001). When the API is enabled, user CRUD goes through the API. HTTP client, DTOs and mappers stay private to `telemt_backend`; handlers, Mini App and `monitor` use only its facade types.
- `src/telemt_cfg.rs` is an internal legacy adapter used by `telemt_backend`; do not call it from UI code. After writing `telemt.toml` rely on `TelemtRuntime::notify_config_reloaded()` (telemt hot-reloads), not on an unconditional restart.
- `src/runtime/` abstracts process control: `systemd` / `external` / `none` (ADR 003). Production default is Docker with `external`, so never assume systemd: gate UI actions on `RuntimeCapabilities`. Raw `systemctl`/`journalctl` calls live only in `src/service.rs`.
- `src/db.rs` + `src/db/*.rs` — SQLite repositories and migrations (`Db::migrate()` on startup, additive changes only). Return data and typed states, never UI strings.
- `src/bot/handlers/`: `commands/` and `callbacks/` are entry points, `actions/` holds use-case orchestration (`db + telemt_backend + reply`), `screens/` renders, `src/bot/keyboards.rs` builds inline keyboards. Keep handlers thin; screens get data via `actions/`.
- `src/webapp/` — Mini App (ADR 005): axum server, `initData` auth in `auth.rs`, JSON API in `api.rs`. It may read and change state via `db` and `telemt_backend`, but reuses existing use-cases from `bot::handlers` (`pub(crate)` re-exports) instead of duplicating them, and never touches `telemt_cfg`/`service`. Frontend in `assets/` is embedded into the binary (no JS build step) — rebuild after edits.
- `src/monitor.rs` — background polling and admin alerts; consumes structured `telemt_backend` snapshots, builds no screens.
- No blocking commands or file I/O in async code: use async APIs or `spawn_blocking` (as in `telemt_cfg.rs`, `update.rs`).

## Domain invariants

- A `telemt` user is `tg_<telegram_user_id>` (`bot::handlers::state::telemt_username`).
- Registration state transitions and invite consumption are conditional (atomic) SQL updates; never replace them with read-then-write.
- Invite tokens respect expiration, `is_active` and `max_usage`; an already approved user re-opening the link does not increase `usage_count`.
- Wizard state is stored in SQLite (survives restarts, TTL `security.wizard_state_ttl_seconds`).
- `/start` is the universal entry: plain start, invite deep link, admin deep link to a screen.
- Partial control API degradation must be shown per section, not hidden behind a generic "no data".

## Adding a config option

Touch all of: `src/config.rs` (field, default, validation) → whitelist in `src/env_config_overlay.rs` if it should be overridable via `TELEMT_ADMIN__*` → `deploy/docker/telemt-admin.docker.toml.example` → config section of `README.md` → ADR 004 if config sources change. Editable bot texts belong in `[bot_messages]`, not in code. Only expose settings an operator would actually tune.

## Bot UX and callbacks

- `BotFather` model: slash command opens an inline screen; `slash -> text wizard` only for short legacy shortcuts. No persistent reply keyboards.
- Text input after an inline button: keep the screen, send a separate prompt with the expected format and a cancel/back path.
- Callbacks opening a screen `edit` the current message; new messages only for prompts, final results and artifacts (link, QR, list, status).
- Screen text must match the available buttons: do not send users to a command when a button is there, do not mention unavailable actions.
- New callbacks: typed payload in `callback_data.rs`, parse errors handled without panic, safe reply to the user.
- New admin scenarios: check rights (`is_admin_message` / `config.is_admin`) → validate → use-case in `actions/` → `tracing` log → clear reply.

## Testing

- Tests live next to code in `#[cfg(test)]` modules (no `tests/` dir). For domain logic and bugfixes write the failing test first.
- Unit-test pure helpers: mappers, formatting, callback payload parsing, validation. SQLite code is tested on a temporary DB (`tempfile`), not SQL mocks.
- Keep tests deterministic: no network, real Telegram API, `systemctl` or system paths; if code is tied to I/O, extract a pure function first.
